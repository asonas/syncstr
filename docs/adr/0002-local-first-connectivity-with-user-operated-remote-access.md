# Local connectivity with optional user-operated remote access

Syncstr must support local device discovery, pairing, and direct music synchronization without external services, and its operator will not provide central connectivity servers. Remote access is optional: listeners who need it supply their own supporting services, including a peer directory and a transfer relay where needed, using deployment templates and instructions supplied with Syncstr. Initial remote access targets an always-on library-holding device such as a NAS; arbitrary roaming-device-to-roaming-device connectivity is outside this initial scope.

Prefer direct transfer and automatically fall back to end-to-end encrypted relayed transfer only when a relay has been configured. A relay is optional, so installations without one may be unable to connect across some networks. This accepts additional setup for remote-access users in exchange for avoiding operator-hosted infrastructure and its recurring costs; an existing personal deployment is not a shared service dependency for other users.

The administrator configures remote-access services on the library-holding device and exports their connection information in a single enrollment QR code. A client should not need to enter each supporting service's URL separately. Discovery on a shared LAN does not grant access: devices require explicit initial pairing, after which paired devices may automatically rediscover and reconnect to one another on that LAN.

Initial enrollment takes place on the LAN. The NAS issues an expiring, single-use pairing invitation through its CLI; a client receives it through a QR code or pasted invitation link and redeems it through the NAS pairing API while proving possession of its device key. Successful redemption authorizes that device and supplies the remote-access configuration. Syncstr does not introduce username/password accounts: subsequent authentication uses the registered device key, and the NAS administrator can revoke a device's authorization. The pairing API must be reachable before enrollment, but access to music requires completed authorization.

Remote-access users may deploy their supporting services on a separately reachable server, such as their own VPS, rather than requiring all services to run on the NAS. Remote-access onboarding should avoid manual router port configuration; the existing manually allowed direct route is verification evidence, not the intended onboarding experience.

The NAS example does not restrict the library host role to headless installations. A desktop playback application can also be a library host, and a cluster may have multiple library hosts exchanging music with each other and playback devices. See [the cluster model discussion](../cluster-model-design.md) for the agreed product model and unresolved storage policies.

These are accepted product boundaries, not a claim that all behavior is implemented. Initially, library hosts issue invitations and revoke members, and their decisions propagate across the cluster. Protocol details and acceptance checks are proposed in [the implementation plan](../cluster-implementation-plan.md); NAS references above describe one deployment of the general library-host role.
